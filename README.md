# SpecialTech AI ERP — Операционный учёт, диспетчеризация и аналитика аренды спецтехники

> **Корпоративная ERP + CRM + AI-платформа для компаний аренды строительной спецтехники (экскаваторы, автокраны, самосвалы, погрузчики, бульдозеры, автовышки) с мультиучастковым учётом, закрывающими документами (Акт, КС-2, КС-3, Счёт), телеметрией ГЛОНАСС/ДУТ и мультиагентным AI на базе Google Gemini.**

---

## 1. Состояние проекта на текущий момент (As-Is vs Target)

Чтобы избежать путаницы между работающим приложением и подготовленной документацией для перехода на серверную БД:

### Что работает прямо сейчас (Live Runtime)
- **Frontend SPA (`React 19 + TypeScript + Vite 8 + Tailwind CSS v4`)**:
  - **13 функциональных разделов** бокового меню + модальные окна операций (`QuickShiftModal`, `NewDealModal`, `ClosingDocsModal`, `CustomerCardModal`, `EquipmentDetailModal`, `ExcelExchangeModal`, `StatusNotificationSettingsModal`).
  - **Хранение данных**: клиентское хранилище браузера **`localStorage`** (19 ключей `specialtech_*`) с начальной загрузкой из `src/data/seedData.ts`. Все изменения сохраняются в браузере без сброса при перезагрузке страницы.
  - **Экспорт документов на клиенте**: `.docx` (`docx` ^9.16.0), `.xlsx` (`xlsx` ^0.18.5), печатные формы A4 HTML/PDF (в т.ч. **Акт оказанных услуг**, **КС-2 ОКУД 0322005**, **КС-3 ОКУД 0322001**, **Счёт на оплату** с автоподсчётом НДС 20% / Без НДС и суммы прописью).
- **Backend Proxy (`server.ts`, Node.js + Express, порт `3000`)**:
  - Монтирует `vite.middlewares` в режиме разработки (`npm run dev`) и отдаёт `dist/` в production (`npm start`).
  - Реализует **5 активных REST POST-эндпоинтов**:
    1. `POST /api/ai-analyst` — 6 специализированных AI-агентов через `@google/genai` (модель по умолчанию `gemini-4-hydrogen`, параметры из Админ-панели) с детерминированным локальным fallback-движком (`local_expert_engine_fallback`) при отсутствии `GEMINI_API_KEY`.
    2. `POST /api/chat-agent` — встроенный LLM-агент раздела «Операционный чат» (`ThinkingLevel.LOW`, строгая JSON-схема `responseSchema`: `answer`, `chatSummary`, `suggestedReply`, `matchedSources[]`).
    3. `POST /api/ocr-shift` — симулятор OCR-распознавания фото счётчика моточасов и путевых листов.
    4. `POST /api/1c/test-connection` — проверка подключения к OData v3 / HTTP-сервису 1С для `ООО «SpecialTech»` и `ИП «SpecialTechnica»`.
    5. `POST /api/telemetry/test-connection` — проверка подключения к серверу ГЛОНАСС/ДУТ/CAN (`Wialon IPS`, `Omnicomm`, `GalileoSky`, `Scout`, `ЕГТС`).

### Реализованный серверный контур (Python FastAPI + PostgreSQL 17)
- **FastAPI Backend (`/backend/`, Python 3.11+ / SQLAlchemy 2.0 asyncpg / Pydantic v2 / Alembic, порт `8000`)**:
  - Подключается к **PostgreSQL 15+ / 17+** (`db/schema.sql` v2.1.0 — **12 схем, 56 таблиц, 3 SQL View**, `db/data_migration.sql`).
  - Реализует полный набор REST-эндпоинтов `/api/v1/*` по спецификации `fastapi_contracts_and_models.txt` (v1.5) с `CamelModel`-сериализацией, JWT-аутентификацией + RBAC (`6 ролей`), изоляцией Контура А (`enforce_branch_scope`, 5-звенный поток водителя, запрет межфилиального перелива ГСМ, Excel-обмен строго по одному участку) и общими реестрами Контура Б (`erp.contracts`, `rag.knowledge_documents`, маршрутизация 1С ООО/ИП, свод филиалов `[ВСЕ]`).
  - Типизированный клиент фронтенда [`src/services/apiClient.ts`](./src/services/apiClient.ts) хранит JWT в оперативной памяти вкладки и обращается к `/api/v1/*`.
  - В [`server.ts`](./server.ts) встроен опциональный прокси `/api/v1/*` → `FASTAPI_BACKEND_URL` (по умолчанию не задан, чтобы standalone-режим с `localStorage` продолжал работать без внешнего Python-сервера).
- **LangGraph RAG-оркестрация (`ai_agents_orchestration_and_rag.txt` v1.2.1)**: спецификация мультиагентного графа с Read-Only SQL-инструментами и векторным поиском по `rag.document_chunks`.

### 2-контурное разделение данных и 5-звенный поток водителя
- **Контур А (обособленный операционный поток по участку `branchId`)**: форма **«Регистрация смены машиниста»** (`QuickShiftModal`) и целевой персональный бот водителя в мессенджере **MAX** объединяют 5 связанных сущностей строго внутри участка:
  **Водитель (`driverId`, телефон MAX) ↔ Корпоративная карта подотчёта (`cardLast4`, лимит) ↔ Участок (`branchId`) ↔ Единица техники (`equipmentId`) ↔ Заказчик (`clientName` + активная заявка/заказ `dealId`/`orderId`)**.
  Также к участку обособленно привязаны: **Fleet Manager и Главный механик участка**, плановое ТО, табели Т-13 и операционный обмен Excel (`.xlsx`, строго 1 участок). Межфилиальный перелив ГСМ (`fuel_for_equipment`) запрещён, а редкий заказчик на двух участках ведётся как отдельный контрагент с префиксом своего участка.
- **Контур Б (единые модули и сводно-аналитические выборки руководителя)**: **«Договоры и юротдел»** (`ContractsView`), **База знаний RAG**, справочники **1С** (`ООО` / `ИП`), **дашборды и сводные таблицы руководителя** (`[ВСЕ]`, `AllBranchesFinancialTables`, `AdminCostTablesSection`, 3-листовой экспорт `branches_summary`) работают без принудительного дробления на участковые базы — как единые реестры или аналитические выборки из баз участков.

### Математическая модель операционной прибыли
$$\text{Операционная прибыль} = \text{Выручка} - \text{Прямые затраты} - \text{Постоянные расходы участка} - \text{Накладные парка}$$

1. **Прямые затраты**: дизельное топливо (ГСМ факт), сдельная ЗП машинистов, ТО/ремонт и запчасти, доставка тралом, субподряд (привлечённая техника).
2. **Постоянные расходы участка (5 упрощённых категорий)**:
   - `office_itr_salary` — Зарплата офис и ИТР (Fleet Manager, ИТР, бухгалтерия — **без** водителей и слесарей ремонта техники);
   - `aho` — АХЧ (аренда офиса, бытовки, канцелярия, оргтехника);
   - `leasing` — Лизинговые платежи за спецтехнику и транспорт;
   - `taxes` — Налоги (транспортный, на имущество, налоговые отчисления);
   - `other` — Прочие постоянные (охрана, предрейсовый медик, ПО/1С/ГЛОНАСС).

## 4. Ключевые функциональные возможности (13 модулей)

1. **Мультиучастковая архитектура (`BranchesView`, `Header`)**:
   - Изолированные потоки CRM/ERP и документов для каждого участка (`MSK` Москва, `KZN` Казань и создаваемые филиалы) или консолидированный режим директора (`[ВСЕ]`).
   - В настройках каждого участка закреплены **Fleet Manager** и **Главный механик участка** (`chiefMechanicName`, `chiefMechanicPhone`).
   - Автоматическая каскадная синхронизация префиксов (`orderPrefix`, `waybillPrefix`, `shiftPrefix`, `actPrefix`, `oneCDepartmentCode`) во всех существующих заказах, сделках, сменных рапортах, закрывающих документах (КС-2, Акт, КС-3, Счёт), договорах, алертах и сообщениях чата.
2. **Главный BI-дашборд и свод по филиалам (`DashboardView`, `AllBranchesFinancialTables`)**:
   - Фильтрация по конкретной дате, месяцу или за год («Все»).
   - Рейтинг техники по операционной прибыли с выделением самосвалов (учёт пробега и количества рейсов `tripsCount`), структура прямых расходов (включая «Субподряд») и 5 категорий постоянных расходов с детализацией.
   - В режиме `[ВСЕ]` — 3 сводные таблицы по филиалам («Прибыли», «Расходы», «Сводный финансовый расчёт») и их выгрузка в 3-листовой Excel (`exportBranchesSummaryToExcel`).
3. **Поле Fleet Manager, Водители и Карта подотчёта (`FleetManagerView`, `TimesheetsView`, `DriverBindingPanel`, `QuickShiftModal`)**:
   - Привязка водителей к технике и корпоративным картам подотчёта (`cardLast4`, `cardLimitRub`) строго в пределах участка; выбор основного или сменного экипажа по табелю (`Я / Н / В / Б / О`), оперативные замены со стороны Fleet Manager или Администратора.
   - Форма «Регистрация смены машиниста» (`QuickShiftModal`) автоматически связывает единицу техники с водителем, его картой `*last4` и активным заказчиком/заявкой (`dealId`/`orderId`), формирует путевой лист ПЛ, фиксирует перегон (`relocationHours`), «Платежи» и внутриучастковый перелив ГСМ (`fuel_for_equipment`) без блокировки техники.
   - Закрытие смен по активным заявкам CRM (`DealShiftLog`, до 2 смен 1/2 на дату) с отметкой в чат и модерация сменных рапортов.
4. **Закрывающие документы по стандартам РФ (`ClosingDocsModal`, `RentalsView`, `closingDocuments.ts`)**:
   - Формирование, сохранение в реестр и печать/скачивание (A4 HTML/PDF + `.docx`) 4 форм:
     * **Акт оказанных услуг / выполненных работ** (`act_services`);
     * **Унифицированная форма № КС-2** (`ks2`, ОКУД `0322005`);
     * **Справка о стоимости работ № КС-3** (`ks3`, ОКУД `0322001`);
     * **Счёт на оплату услуг** (`invoice`, с банковским ПП и расчётом НДС 20% для ООО / Без НДС для ИП).
   - Настраиваемые уведомления о статусах документов и оплаты (`StatusNotificationSettingsModal`).
5. **Операционный чат, встроенный LLM-агент и Бот MAX (`ChatView`, `MaxCustomerBotPanel`)**:
   - Обмен сообщениями, реквизитами, фото объектов и подтверждениями смен (контролируется глобальным флагом «Админ: ВКЛ/ВЫКЛ»).
   - Встроенный **LLM-ассистент чата** (`/api/chat-agent`) отвечает на вопросы по переписке и базе ERP со ссылками на найденные источники и готовым черновиком ответа.
   - Панель клиентского бота **MAX** для приёма заявок заказчиков с авто-маршрутизацией в 1С.
6. **Юридический реестр и База знаний (`ContractsView`, `KnowledgeBaseView`)**:
   - Управление договорами, допсоглашениями, спорами, претензиями и шаблонами; неизменяемый журнал аудита (`legal_history`); автооткрытие договора/оферты из карточки клиента (`CustomerCardModal`).
   - Экспорт документов в 6 форматов (`DOCX`, `PDF`, `XLSX`, `HTML`, `TXT`, `JSON`) и публикация в Базу знаний с автоматическим обезличиванием реквизитов (`anonymizeLegalText`).
7. **Двухконтурная интеграция 1С и Администрирование ГЛОНАСС (`Integrations1CView`, `AdminPanelView`)**:
   - Раздельная маршрутизация ЮЛ (договор → `ООО «SpecialTech»`, ОСНО) и ФЛ (с договором / без договора по оферте → `ИП «SpecialTechnica»`, УСН).
   - Настройки колонок таблиц UI, моделей LLM, параметров RAG, порогов датчиков ГЛОНАСС/ДУТ/CAN и IMEI-привязок техники, таблиц постоянных/переменных затрат.

## 5. Ролевая модель доступа (RBAC — `adminConfig.ts`)

В системе настроены 6 ролей с разграничением прав на страницы (`edit / view / hidden`) и чувствительные поля (маржинальность, ЗП, телефоны MAX, таблицы затрат):

| Роль (`SystemRoleId`) | Назначение и ключевые права |
| :--- | :--- |
| **`admin` (Администратор)** | Полный доступ ко всем 13 разделам, матрице прав, настройкам LLM/RAG/ГЛОНАСС, таблицам затрат и глобальному разрешению подтверждений. |
| **`top_manager` (Руководитель)** | Консолидированная аналитика всех участков, P&L, маржинальность, таблицы постоянных и переменных расходов, AI-Аналитик. |
| **`fleet_manager` (Начальник участка)** | Операционное управление участком: Поле Fleet Manager, парк, аренда, CRM, табели/смены, замены водителей, чат (без доступа к 1С и админ-панели). |
| **`lawyer` (Юрист)** | Полное управление разделом «Договора» и «База знаний» (договоры, споры, претензии, обезличивание), просмотр аренды, CRM и AI-Юриста. |
| **`accountant` (Бухгалтер)** | Проведение закрывающих документов (Акт, КС-2, КС-3, Счёт), контроль оплат и дебиторки, таблицы затрат и настройка обмена с 1С (ООО/ИП). |
| **`driver` (Водитель / Бот MAX)** | Просмотр своих смен/табеля, подача рапортов ЭСМ-7, отметка корпоративной карты и перелива ГСМ, чат участка и база знаний. |

## 6. Локальный запуск приложения

### Предварительные требования
- Node.js 20+ и npm
- Опционально: `GEMINI_API_KEY` в `.env` (или в панели Secrets) для живых ответов Gemini API (без ключа `/api/ai-analyst` работает через локальный fallback-движок).

### Команды разработки и сборки
```bash
# 1. Установка зависимостей
npm install

# 2. Настройка переменных окружения
cp .env.example .env

# 3. Запуск Express-сервера и Vite SPA на порту 3000
npm run dev

# Проверка типов TypeScript и сборка production-бандла
npm run lint
npm run build
npm start
```

Приложение будет доступно по адресу `http://localhost:3000`.

## 7. Запуск полной связки PostgreSQL 17 + Python FastAPI + Frontend (на ПК или сервере)

### Шаг 1. База данных PostgreSQL 17
```bash
# 1. Создать базу данных
psql -U postgres -c "CREATE DATABASE specialtech_erp ENCODING 'UTF8';"

# 2. Накатить полную схему (v2.1.0 — 12 схем, 56 таблиц, 3 View; работает и без pgvector)
psql -U postgres -d specialtech_erp -f db/schema.sql

# 3. Загрузить начальные данные (участки MSK/KZN, пользователи, техника, карты, ГЛОНАСС, RAG)
psql -U postgres -d specialtech_erp -f db/data_migration.sql
```

### Шаг 2. Бэкенд Python FastAPI (`backend/`, порт `8000`)
```bash
cd backend
python -m venv .venv
# Linux / macOS:
source .venv/bin/activate
# Windows (PowerShell):
# .\.venv\Scripts\Activate.ps1

pip install -r requirements.txt
cp .env.example .env
# Отредактируйте backend/.env: укажите DATABASE_URL, надёжный JWT_SECRET_KEY и BOOTSTRAP_SETUP_TOKEN

uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Проверка здоровья БД и API: `http://localhost:8000/api/v1/health` и OpenAPI Swagger `http://localhost:8000/docs`.

> **Первичная установка пароля администратора:** в `db/data_migration.sql` содержатся шаблонные хеши. После задания `BOOTSTRAP_SETUP_TOKEN` в `backend/.env` установите рабочий пароль для `admin@specialtech.ru` (или других учётных записей) через `POST /api/v1/auth/bootstrap-password`, после чего входите через `POST /api/v1/auth/login`.

### Шаг 3. Подключение фронтенда к FastAPI
В корневом `.env` укажите адрес запущенного FastAPI:
```env
FASTAPI_BACKEND_URL=http://127.0.0.1:8000
VITE_API_MODE=fastapi
```
После этого запустите `npm run dev` — Express-сервер на порту `3000` автоматически проксирует все запросы `/api/v1/*` в FastAPI, а если `FASTAPI_BACKEND_URL` не задан, приложение продолжает работать в автономном браузерном режиме.

Подробный реестр всех таблиц, индексов и файлов БД приведён в [`docs/DATABASE_REGISTRY.md`](./docs/DATABASE_REGISTRY.md).
